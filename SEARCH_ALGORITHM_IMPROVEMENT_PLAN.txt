TURBO SEARCH FOR WOOCOMMERCE
SEARCH ALGORITHM PERFORMANCE IMPROVEMENT PLAN
================================================

Document status: Living review document
Created: 2026-09-04
Last updated: 2026-09-05 (Findings D-H implemented and released as 1.10.0,
  two rounds of reviewer follow-up audit addressed, deployed and live-
  verified on thogotodeli.com)
Plugin version reviewed: 1.10.0 (DB schema at Activator::DB_VERSION 1.10.0)
Scope: Search latency, database efficiency, throughput, and cache effectiveness


PURPOSE
-------

This document tracks high-impact opportunities for improving the search
algorithm. It should be reviewed and updated whenever the search query path,
index schema, caching strategy, load-test results, or supported database
versions change.

Do not implement an optimization solely because it appears promising here.
Each change must be benchmarked against the existing implementation and must
preserve acceptable search relevance.


CURRENT BASELINE
----------------

The current search path already provides:

1. A dedicated InnoDB product-search table.
2. Combined and title-only FULLTEXT indexes.
3. Indexed normalized-SKU prefix lookup.
4. Tiered FULLTEXT, prefix, and substring matching.
5. APCu, WordPress transient, and browser-session caching.
6. Cache-stampede protection when a persistent object cache is available.
7. Client-side debouncing and cancellation of obsolete requests.
8. Separate rate limiting for expensive fallback searches.

The main remaining performance risk is cold-cache queries that fall through to
prefix and leading-wildcard LIKE searches.


PRIORITY 1: REPLACE LEADING-WILDCARD TABLE SCANS
------------------------------------------------

Status: Downgraded — problem statement overstated relative to the current
        code; narrowed to a smaller cleanup, not implemented in this pass.
Expected impact: Low-medium (was: Very high)
Complexity: High
Relevant code: includes/class-search-handler.php, substring and any-word tiers

2026-09-04 feasibility review:

Re-read against the actual query_database() implementation: leading-wildcard
`%term%` LIKE against `content` is NOT routine today. It appears in exactly
two places, both already gated to rare fallback paths:

- Tier 3 substring fill (query_database(), gated on `0 === $fulltext_count`)
  — only runs when FULLTEXT found literally nothing.
- The any-word LIKE relaxation — only runs when every earlier tier returned
  zero results, and only for 2+ word queries.

Both are additionally covered by the separate, stricter "expensive fallback"
rate limiter (wcs_fallback_rate_limit_requests/window) already listed under
baseline item 8 in this document. Tier 1's own short-word LIKE clause is not
a table scan either — it is ANDed onto rows the FULLTEXT MATCH() clause in
the same query already narrowed via the index, not evaluated against the
whole table. Tier 2 uses prefix-only LIKE ('term%'), which is index-served
via idx_title_prefix/idx_sku.

So the acceptance criterion "no routine leading-wildcard scan over content"
is close to already true, and the ngram/side-table rebuild this priority
proposed is not justified by what is actually left to fix. Left as a
narrower future cleanup (e.g. dropping the content branch of the any-word
relaxation specifically) rather than implemented as originally scoped.

Problem (as originally written — kept for context, see note above):

The substring and any-word fallback tiers use patterns such as `%term%` against
title, SKU, and content. A conventional B-tree index cannot serve a
leading-wildcard lookup, so these fallbacks can scan and score much of the
search table. Content is a LONGTEXT column, making this particularly expensive
for large catalogs and concurrent searches.

Suggested direction:

- Replace substring scans with an indexed token or ngram side table; or
- use the database FULLTEXT ngram parser where reliably available; or
- restrict substring recovery to smaller indexed fields and omit content scans
  from interactive typeahead.

Acceptance criteria:

- No routine leading-wildcard scan over the content column.
- Materially lower p95 latency for zero-result and short-word searches.
- Relevance tests demonstrate that important partial matches remain available.


PRIORITY 2: RETRIEVE CANDIDATES, THEN RERANK
--------------------------------------------

Status: IMPLEMENTED AND VERIFIED LIVE (2026-09-04) — the original IN-subquery
        form was confirmed broken (see "release blocker" note below, now
        resolved), rewritten as a derived-table JOIN, and re-verified against
        a live MariaDB instance (thogotodeli.com).
Expected impact: High for broad queries and large catalogs
Complexity: Medium to high
Relevant code: includes/class-search-handler.php, fulltext_sql()

Implementation notes:

fulltext_sql() runs as a two-stage retrieval: an inner derived-table subquery
selects product_id only, filtered by the same MATCH()/short-word/stock
clauses as before and ordered by the cheap combined-index MATCH() score,
bounded by LIMIT wcs_candidate_limit (default 200, filterable, always >= the
requested result count via `max( $limit, ... )`). The outer query
INNER JOINs the real table (aliased `t`, since the derived table also exposes
product_id) to that bounded candidate set and applies the full weighted
formula (multiple MATCH() calls, IF()/LOG() boosts) only there, before the
final LIMIT. product_id is the table's PRIMARY KEY, so the JOIN can never
produce more rows than the subquery returned, regardless of any other
clause — this is what actually bounds the reranking cost, not a
query-planner assumption.

$short_sql/$stock_clause were kept on the INNER subquery deliberately (not
duplicated on the outer query): they are real filters that must apply before
the candidate LIMIT truncates the set, or a non-matching row could occupy a
candidate slot a genuine match needed.

Known tradeoff (this is the acceptance-criteria risk called out below, not a
bug): a row ranked outside the candidate window by the cheap MATCH() score
never reaches the full formula, even if that formula would have scored it
highly (e.g. via the exact-title boost). In practice an exact title/SKU match
also contains every query term and should score highly on the cheap MATCH()
score too, and the Tier 0 SKU-normalized probe already short-circuits exact
SKU lookups before FULLTEXT ever runs — but per-catalog ranking-quality
regression has NOT been benchmarked (only SQL correctness/execution has been
verified — see below). Widen via `add_filter( 'wcs_candidate_limit', ... )`
for a store where ranking regressions are observed.

Testing performed: PHPUnit unit tests updated (SearchHandlerQueryTest,
"Candidate-then-rerank" group) verifying the SQL shape — the INNER JOIN to a
derived table, the inner LIMIT defaulting to 200, the wcs_candidate_limit
filter, and the `max($limit, ...)` floor. These tests run against the
project's fake $wpdb and validate SQL *construction*; they cannot and did not
catch the release blocker recorded below — that required real execution.

2026-09-04 — SQL COMPATIBILITY BUG FOUND, FIXED, AND VERIFIED LIVE:

An earlier version of this implementation used:

    WHERE product_id IN (
        SELECT product_id ... ORDER BY ... LIMIT 200
    )

A follow-up review (the "2026-09-04 implementation audit" entry in the
REVIEW LOG) correctly flagged this as invalid: MySQL and MariaDB reject LIMIT
inside an IN/ALL/ANY/SOME subquery with error 1235 ("This version ... doesn't
yet support 'LIMIT & IN/ALL/ANY/SOME subquery'"). This was independently
confirmed by running the exact query shape against a live database — see
below — rather than taken on the audit's word alone, since the audit itself
is a claim to verify like any other.

Verification (live, against thogotodeli.com's production MariaDB 10.11.18,
per this repo's own "test live, not local dev" rule and no local MySQL/
MariaDB being available):

- The IN-subquery form reproduced the exact reported error:
  `ERROR 1235 (42000): This version of MariaDB doesn't yet support
  'LIMIT & IN/ALL/ANY/SOME subquery'` — confirming the audit's finding.
- Rewritten as an INNER JOIN against a derived table (`... FROM t INNER JOIN
  (SELECT product_id FROM ... LIMIT n) AS candidates ON candidates.product_id
  = t.product_id`), which has no such restriction on any MySQL/MariaDB
  version. This form was verified to execute correctly against the same live
  database, including the full weighted ranking formula, and separately
  re-verified with $short_sql and $stock_clause both populated (the hybrid
  Tier 1 path) — both returned correct, sensibly-ranked results against the
  real ~1995-row TEST- product catalog.
- fulltext_sql() and its PHPUnit coverage were updated to the JOIN form (all
  264 tests passing, phpcs clean).

This is now resolved. Not yet done: a controlled p95/EXPLAIN benchmark and a
broader relevance-regression pass against the full required benchmark query
groups below — this fix confirms the query is *executable and correct*, not
that its candidate-limit tradeoff has been latency/relevance-benchmarked.

Problem:

The FULLTEXT query computes several MATCH expressions plus LIKE, CONCAT, IF,
and logarithmic scoring expressions before LIMIT is applied. Broad searches can
therefore perform detailed ranking work across a large candidate set even
though only a few dropdown results are returned.

Suggested direction:

Use two-stage retrieval:

1. Select a bounded candidate set, initially 50-200 rows, using the inexpensive
   combined FULLTEXT score.
2. Apply the detailed relevance formula only to those candidates.

The candidate limit must be selected through relevance and latency benchmarks.
A limit that is too small may prevent an exact title, SKU, or high-quality
business-ranking signal from reaching the reranking stage.

Acceptance criteria:

- Lower database CPU and p95 latency for broad FULLTEXT searches.
- No material deterioration in top-six ranking quality.
- Candidate size is justified by repeatable benchmark results.


PRIORITY 3: REDUCE SECONDARY PREFIX QUERIES
-------------------------------------------

Status: REJECTED (2026-09-04) — conflicts with an already-implemented,
        deliberate design decision. Not implemented.
Expected impact: High for cold-cache throughput
Complexity: Medium
Relevant code: includes/class-search-handler.php, Tier 2 prefix fill

2026-09-04 feasibility review:

This priority proposes running Tier 2 (prefix LIKE fill) only when FULLTEXT
returns zero results, instead of whenever FULLTEXT comes up short of the
requested count. The code's own inline comment at the Tier 2 site records
that this was already tried and deliberately reversed: Tier 2 used to run
only on zero results, and was changed to run whenever FULLTEXT came up SHORT
because the old behavior was "pure lost recall" — a FULLTEXT pass returning
1 row against a 6-row limit was leaving 5 slots unfilled that real prefix
matches could have covered. The same comment notes Tier 2 is index-served
(idx_title_prefix/idx_sku) and therefore cheap — "free by comparison" to the
Tier 3 substring scan, which is why Tier 3 alone kept the stricter
zero-results-only gate.

Implementing this priority as written would revert that considered recall
fix for a savings the code's own prior review already judged not worth it.
Dropped rather than implemented. If cold-cache throughput on Tier 2 is later
found to be a real problem on a specific large catalog, that should be
re-measured on its own — not assumed from this document alone — since it
would be knowingly trading away recall the codebase fixed once already.

Problem:

The prefix tier runs whenever FULLTEXT returns fewer rows than the configured
result count. This means a successful FULLTEXT search may still execute a
second database query simply to fill every dropdown slot.

Suggested direction:

Run the prefix-fill query only when one of these conditions is true:

- FULLTEXT returned no results.
- The query contains words below the active FULLTEXT token-length threshold.
- Testing demonstrates that the missing results have meaningful value.
- An optional maximum-recall mode explicitly requests the extra work.

Acceptance criteria:

- Fewer database queries per cold-cache search.
- Improved concurrent request throughput.
- Any reduction in recall is measured and considered acceptable.


PRIORITY 4: PRECOMPUTE NORMALIZED RANKING FIELDS
------------------------------------------------

Status: IMPLEMENTED (2026-09-04)
Expected impact: Medium to high
Complexity: Medium (confirmed — matched an existing schema-migration pattern)
Relevant code: includes/class-activator.php and includes/class-indexer.php

Implementation notes:

Added a single precomputed column, `title_padded` (= ' ' . title . ' '),
following the exact pattern already established for `sku_normalized`:
computed once at index time in Indexer::apply_row_filter_and_sanitize()
(the single source of truth shared by both the per-product and bulk-rebuild
indexing paths), stored as a plain TEXT column (no DEFAULT literal on a TEXT
column — MySQL 5.7/8.x reject that; matches the existing `title`/`content`
column definitions), and read directly by the query layer instead of
computing CONCAT(' ', title, ' ') fresh on every candidate row for every
query word (the phrase boost in fulltext_sql(), and the per-word scoring
loop shared by Tiers 2/3 and the any-word relaxation — a query with N words
against M candidate rows previously ran that CONCAT M*N times per request).

Schema: Activator::DB_VERSION bumped 1.9.0 -> 1.9.1; REBUILD_REQUIRED_BELOW
bumped 1.8.0 -> 1.9.1 so upgrading installs get one full rebuild and every
row gets title_padded populated promptly, rather than degrading silently
(an empty title_padded on an un-rebuilt row just means the phrase boost
contributes 0 for that row until reindexed — not broken, but worth avoiding).
This mirrors exactly how sku_normalized/total_sales/etc. were rolled out.

Did NOT add title_words/token-prefix columns from the original suggestion
list — nothing in the current query path would consume them, and adding
unused columns is exactly what the acceptance criteria below warn against
("avoid storing fields that do not remove measurable work from the request
path"). Revisit if a future priority needs them.

Testing: PHPUnit suite updated (SearchHandlerQueryTest and IndexerTest — the
canonical-column-order regression test in particular) and passing (264
tests). phpcs clean. Like Priority 2, the actual CPU savings have not been
measured against a live catalog — this is a mechanical, low-risk change
whose correctness is verified, but its performance benefit is not.

Problem:

Ranking repeatedly evaluates expressions such as padded-title CONCAT and LIKE
checks. These expressions consume CPU and cannot use ordinary indexes.

Suggested direction:

Compute reusable values during indexing, potentially including:

- title_normalized
- title_words or a padded word-boundary representation
- indexed title/SKU token prefixes

The final schema should be driven by EXPLAIN ANALYZE results. Avoid storing
fields that do not remove measurable work from the request path.

Acceptance criteria:

- Reduced expression work during result ranking.
- Storage and rebuild-time increases remain reasonable.
- Schema upgrades work safely on existing installations.


PRIORITY 5: PREWARM POPULAR SEARCH PREFIXES
-------------------------------------------

Status: Proposed — complexity revised, not implemented in this pass.
Expected impact: Medium to high on active stores
Complexity: Medium-high (was: Medium)
Relevant code: cache invalidation and index-rebuild completion path

2026-09-04 feasibility review:

Hooking a prewarm job onto the existing versioned cache-invalidation flow
(wcs_cache_version bump, deferred via Action Scheduler per ARCHITECTURE.md)
is architecturally natural and confirmed low-risk to wire up. But there is
currently no aggregate prefix-popularity tracking anywhere in this codebase
— that piece is new infrastructure to design and privacy-audit, not a
wire-up of something that already exists. Treat the complexity estimate as
underestimated; budget for the counter/aggregation mechanism itself, not
just the prewarm trigger.

Problem:

Common prefixes such as `sh`, `sho`, and `shoe` produce broad candidate sets
and recur frequently. Immediately after cache invalidation, multiple common
prefixes must be rebuilt through customer requests.

Suggested direction:

Maintain privacy-safe aggregate counts for popular normalized prefixes and
asynchronously prewarm their result caches after an index rebuild or cache
version change. Focus initially on prefixes of two to five characters.

Acceptance criteria:

- No storage of personally identifiable visitor data.
- Improved post-rebuild cache-hit rate and p95 latency.
- Prewarming is bounded and does not delay indexing or overload the database.

FINDING A: RESULT-AFFECTING SETTINGS DO NOT INVALIDATE SEARCH CACHES

Severity: High
Status: CONFIRMED AND FIXED (2026-09-05)
Relevant code: includes/class-search-handler.php,
               includes/class-query-normalizer.php,
               includes/class-indexer.php

Verification: re-read Query_Normalizer::cache_key() (query+currency+
cache_version only) and Indexer::init()'s hook list directly — confirmed no
update_option_wcs_result_count or update_option_wcs_show_out_of_stock hook
existed anywhere in the codebase. The finding was correct as stated.

Fix: added Indexer::on_result_affecting_setting_changed(), registered on both
options in init(), mirroring the existing on_synonyms_changed() pattern
exactly (old/new equality guard, then execute_cache_bust() — an immediate
wcs_cache_version bump, not the deferred 5-minute product-save path). Test
coverage added (IndexerTest: bump-on-change, no-bump-when-unchanged, for both
options; InitAndBatchLifecycleTest: both hooks are actually registered on
init()). 270 tests passing, phpcs clean.

The server cache key contains the normalized query, currency, and
wcs_cache_version. It does not contain wcs_result_count or
wcs_show_out_of_stock. Indexer registers cache-invalidation hooks for indexed
field settings and synonyms, but not for either of these two settings.

Consequently, changing the result count or out-of-stock visibility can keep
serving results computed under the previous setting until the existing
24-hour transient expires or an unrelated index/cache-version event occurs.
The five-minute APCu entry can preserve the same stale payload in front of the
transient. A browser tab may also retain its own in-memory result until reload.

Suggested fix:

- Immediately bump wcs_cache_version when wcs_result_count or
  wcs_show_out_of_stock changes.
- Use the same old-value/new-value equality guard used by the synonym hook.
- Add request-level tests proving a warmed query is recomputed after either
  setting changes.

Acceptance criteria:

- A result-count change is reflected on the next search request.
- An out-of-stock visibility change is reflected on the next search request.
- Unchanged option writes do not cause unnecessary invalidation.


FINDING B: A NORMALIZED-SKU PREFIX HIT SHORT-CIRCUITS ALL OTHER RELEVANCE

Severity: Medium
Status: CONFIRMED AND PARTIALLY FIXED (2026-09-05) — the false-suppression
        bug is fixed; the "rank as a candidate rather than fallback" part of
        the suggested fix is deferred (see note below).
Relevant code: includes/class-search-handler.php, Tier 0 SKU probe

Verification: re-read the Tier 0 probe — confirmed it was a prefix LIKE
(`sku_normalized LIKE 'query%'`) with an immediate return on ANY hit, exactly
as described. Reproduced the exact reported failure shape live against
thogotodeli.com: `sku_normalized LIKE 'test%'` returns six rows (testeg30,
testbs500, testcs500, ...), none of them an exact match for "test" — under
the old code a literal query "test" would have returned only these, silently
suppressing any genuine title/content match elsewhere in the catalog. The
finding was correct as stated.

Fix (implemented): the immediate short-circuit now fires only on an EXACT
normalized-SKU match (`$row['sku_normalized'] === $sku_norm`), which is the
one case genuinely deterministic enough to justify skipping every other
tier. A prefix-only hit (no exact match) no longer returns immediately —
it falls through and lets Tier 1/2/3 and the relaxation passes run normally,
so a real FULLTEXT/title match can no longer be suppressed by an unrelated
SKU merely starting with the same digits. The prefix rows are not discarded
either: they are kept as a last-resort fallback, used only if every other
tier and relaxation pass still finds nothing at all — so a query that
genuinely only matches via SKU prefix still returns something instead of an
empty dropdown.

Deferred (not implemented): the suggested fix's other option — treating
prefix hits as ranked candidates merged into the normal result set rather
than an all-or-nothing fallback — was NOT implemented. That requires design
work this audit itself flagged as unresolved ("benchmark the extra query/
merge cost and define deterministic duplicate and ordering behavior"), and
rushing a merge/dedup/ordering scheme without that benchmarking would risk
trading one correctness bug for a subtler one. The last-resort fallback
implemented here satisfies the finding's stated acceptance criteria (exact
SKU still fast-paths; a mere prefix hit can no longer suppress a stronger
match) without that additional risk.

Testing: three tests added/replaced in SearchHandlerQueryTest — exact match
still short-circuits (and the internal sku_normalized column never leaks
into the public result shape), a prefix-only hit yields to a real FULLTEXT
match, and a prefix-only hit is used when nothing else matches at all. Also
verified live: the modified SELECT list (now including sku_normalized)
executes correctly against thogotodeli.com's live MariaDB.

Every digit-containing query whose normalized form is at least four characters
runs an indexed `sku_normalized LIKE 'query%'` probe. Any hit returns
immediately and bypasses FULLTEXT, title, content, and later fallback tiers.
The implementation comment describes such a hit as deterministic intent, but
the predicate is a prefix match rather than equality. For example, a query for
`ABC1` can return only products with SKUs `ABC10`, `ABC11`, etc. and omit a
strong title/content match for `ABC1` whose SKU differs.

Suggested fix:

- Preserve the immediate short-circuit for an exact normalized-SKU equality.
- Treat normalized-SKU prefix hits as ranked candidates or as a fill tier, so
  they do not suppress stronger non-SKU matches.
- Benchmark the extra query/merge cost and define deterministic duplicate and
  ordering behavior.

Acceptance criteria:

- Exact normalized SKU still ranks first and retains the fast path.
- A mere SKU-prefix hit cannot suppress an exact-title or stronger FULLTEXT
  result.
- Multiple products sharing an SKU prefix have stable, documented ordering.


FINDING C: PHP STOPWORDS DO NOT COVER THE DEFAULT INNODB STOPWORD LIST

Severity: Medium
Status: CONFIRMED AND FIXED (2026-09-05)
Relevant code: includes/class-query-normalizer.php, STOPWORDS and
               remove_stopwords()

Verification: did not take the specific word list on trust (the audit's own
list of missing words is itself a claim). Queried
INFORMATION_SCHEMA.INNODB_FT_DEFAULT_STOPWORD directly on thogotodeli.com's
live MariaDB — its default list is exactly: a, about, an, are, as, at, be,
by, com, de, en, for, from, how, i, in, is, it, la, of, on, or, that, the,
this, to, und, was, what, when, where, who, will, with, www. Confirmed com,
de, en, la, und, www were indeed absent from STOPWORDS. The finding was
correct.

Fix: added the six missing words to STOPWORDS with a comment explaining they
are not English function words but are still in the live-confirmed default
InnoDB list, so omitting them lets one become a required `+word` BOOLEAN
MODE term the index never tokenized. Test added
(test_stopwords_cover_the_full_default_innodb_ft_list) proving "cafe de"
drops "de" and all six words are present in the constant.

The broader configuration-limit point the finding raised (a server can run a
custom InnoDB stopword table, which no fixed PHP list can universally match)
is NOT addressed — recording and adapting to a live server's actual active
stopword configuration is a real feature, not a one-line fix, and is left
for a future priority if a customer's non-default configuration is reported.

The source says Query_Normalizer::STOPWORDS is a superset of InnoDB's default
stopword list, but it omits at least `com`, `de`, `en`, `la`, `und`, and `www`
from MySQL's documented INNODB_FT_DEFAULT_STOPWORD list. In a multi-word query,
an omitted database stopword can become a required `+word` BOOLEAN MODE term
that the index never stored. That makes the strict FULLTEXT query unmatchable
and pushes a legitimate query such as `cafe de` into slower fallback tiers.

There is a broader configuration limit: MySQL and MariaDB can use custom
InnoDB stopword tables, so no fixed PHP constant can be guaranteed to match
every server's active FULLTEXT configuration.

Suggested fix:

- At minimum, add the missing default InnoDB stopwords and regression tests.
- Determine and record the active server stopword configuration when the
  FULLTEXT index is created, or explicitly install/manage a plugin-owned
  stopword configuration if operationally acceptable.
- Keep the existing wcs_stopwords filter for catalog-specific adjustments.

Acceptance criteria:

- Queries containing a default InnoDB stopword do not become unmatchable
  merely because the word was required by the PHP query builder.
- Behavior with a custom server stopword table is documented and tested, or
  detected reliably enough to keep query construction aligned with the index.


CANDIDATE-WINDOW RELEASE VALIDATION REMAINS OPEN

Priority 2's derived-table JOIN is executable, but its default 200-row window
still needs the relevance and performance validation already required by this
plan. Candidate selection orders only by the combined FULLTEXT score. A row
outside that window never receives the outer exact-title, exact-SKU, title,
stock, or sales boosts. Do not treat live SQL execution as evidence that 200
is the correct cutoff.

Required evidence before release:

- Top-six relevance comparison against the previous unbounded ranking query,
  including broad queries with more than 200 matching products.
- Explicit exact-title and exact-SKU cases placed near/outside the cheap-score
  boundary.
- EXPLAIN ANALYZE plus p50/p95/p99 and database CPU measurements for candidate
  limits such as 50, 100, 200, and an unbounded control.
- A catalog-size-based or measured justification for the shipped default.

FINDING D: PARTIAL REBUILD FAILURES CAN REPLACE A COMPLETE LIVE INDEX
          WITH AN INCOMPLETE ONE

Area: Code & Functionality
Impact: High
Status: Confirmed in source; proposed
Relevant code: includes/class-indexer.php, do_process_batch() and
               index_products_bulk()

When a bulk chunk fails, do_process_batch() retries every product in that
chunk through the single-product path. Individual exceptions increment
$batch_failures, but the rebuild continues unless every attempted product in
the whole batch failed. The cursor and processed count advance across failed
products, and the final safeguard checks only whether staging contains at
least one row. A rebuild with one or more permanently failed products can
therefore swap its incomplete staging table into production and silently make
those products unsearchable.

The fallback is weaker than its control flow suggests: do_index_single_product()
does not check the return value of either `$wpdb->replace()` call. A failed
single-row write normally returns false rather than throwing, so it may not
increment $batch_failures at all. The same unchecked path handles ordinary
incremental product updates, allowing a live index write to fail silently too.

This is especially damaging because the old live table was complete and is
discarded by the atomic rename. A malformed filtered row, an isolated database
error, or a product-specific WooCommerce extension failure can turn a localized
indexing problem into persistent catalog omissions without an admin-visible
error.

Recommended solution:

- Treat any unresolved per-product failure as a failed batch, so Action
  Scheduler retries the same cursor/epoch without advancing past missing rows;
  or keep an explicit failed-ID set and retry it before the final swap.
- Check every single-row `$wpdb->replace()` result and convert false into a
  logged exception/failure result before advancing the rebuild cursor or
  claiming that an incremental update succeeded.
- After the bounded retry policy is exhausted, preserve the old live index,
  clear the indexing flag, and record a specific rebuild error containing the
  failed count/IDs in logs.
- Before swapping, compare staging coverage with the set of eligible products
  or maintain an expected/inserted count during the rebuild. The existing
  `SELECT 1` guard proves only that staging is nonempty.

Tradeoffs and risks:

- One pathological product can prevent a new index from shipping. Preserving
  the known-good live index is safer than silently publishing an incomplete
  one; the UI/log must identify the failing product so the store can recover.
- A final count query can be expensive on a very large catalog. Maintaining
  counters during the cursor walk or validating only failed-ID bookkeeping is
  cheaper, provided concurrent creates/deletes remain correctly accounted for.

Acceptance criteria:

- One failed product cannot be skipped while the rebuild reports success.
- A failed single-row REPLACE is detected in both rebuild and incremental paths.
- A failed rebuild never replaces the existing live index.
- The admin receives an actionable error and the failed product is identifiable
  in WooCommerce logs.
- Tests cover one failure among otherwise successful products and verify that
  no RENAME TABLE occurs.


FINDING E: VARIATION CHANGES DO NOT RELIABLY REINDEX THE PARENT PRODUCT

Area: Code & Functionality / Search Data Freshness
Impact: High
Status: Confirmed in source; proposed
Relevant code: includes/class-indexer.php, Indexer::init(),
               queue_product_update(), and do_index_single_product()

The parent search row contains variation SKUs and the variable product's price
range, so variation changes must refresh the parent. The implementation knows
how to redirect a queued variation to its parent, but its registered live hooks
cover `woocommerce_update_product`, `save_post_product`, and
`woocommerce_product_set_stock_status`. WooCommerce emits distinct hooks for
variations, including `woocommerce_update_product_variation` and
`woocommerce_variation_set_stock_status`; this plugin does not register them.
`save_post_product` also does not match the `product_variation` post type.

As a result, editing a variation SKU, price, publication state, or stock can
leave the parent's indexed variation-SKU text, displayed price range, or stock
state stale until some separate parent save or full rebuild happens. This is a
common operation on variable-product stores and directly affects both finding
products and the correctness of the dropdown.

Recommended solution:

- Register `woocommerce_update_product_variation` and
  `woocommerce_new_product_variation`; resolve their variation ID to the parent
  and queue the parent once through the existing per-request deduplication.
- Register `woocommerce_variation_set_stock_status` for stock-only updates.
- Cover variation trash/delete/restore paths so removed SKUs disappear and
  restored/new SKUs become searchable.
- Keep parent reindexing asynchronous and deduplicated because saving the
  variation editor can emit many hooks in one request.

Tradeoffs and risks:

- A product with many edited variations can otherwise enqueue the same parent
  repeatedly. The existing `$queued_ids` guard and Action Scheduler pending-
  action check should be reused.
- Parent aggregate price/stock lookup data must be updated before the queued
  action runs. Using WooCommerce's post-save variation hooks preserves that
  ordering better than low-level meta hooks.

Acceptance criteria:

- Changing, creating, deleting, trashing, or restoring a variation refreshes
  its parent search row.
- Variation SKU and price changes appear after the queued action without a full
  rebuild.
- Multiple variation hooks in one request enqueue at most one parent update.


FINDING F: DATABASE READ FAILURES ARE CACHED AS LEGITIMATE ZERO RESULTS

Area: Code & Functionality / Reliability
Impact: High
Status: Confirmed in source; proposed
Relevant code: includes/class-search-handler.php, get_rows(), query_database(),
               and handle_request()

get_rows() suppresses database errors and converts every non-array result to an
empty array. query_database() cannot distinguish that from a successful query
with no matches, so it may execute more fallback queries and then return an
empty result. Once the first build has completed, handle_request() caches that
empty result for 24 hours in the transient layer and five minutes in APCu.

A temporary database error, a migration/schema mismatch, or a malformed query
introduced by an extension can therefore become a long-lived false "no
products found" response even after the database recovers. Suppressing the
underlying error also removes the operational signal needed to diagnose the
failure.

Recommended solution:

- Have get_rows() return or throw a typed query-failure signal when
  `$wpdb->last_error` is nonempty, while retaining an empty array for a
  successful zero-row query.
- Stop the tier cascade on an actual query failure, release the cache mutex,
  and return a temporary 503 response or a non-cacheable empty response with a
  diagnostic header appropriate for the frontend.
- Log the SQL tier and sanitized database error through the existing
  WooCommerce logger, with rate limiting to avoid log floods during an outage.

Tradeoffs and risks:

- Returning 503 lets the frontend show an error instead of a misleading empty
  dropdown, but the JavaScript error state must remain unobtrusive and retry on
  the next keystroke/request.
- Database messages can contain implementation details. Keep them in admin
  logs; expose only a generic status to public clients.

Acceptance criteria:

- A database error is never written to APCu or a search-result transient as an
  empty result.
- The mutex is released on all failure paths.
- A subsequent healthy request recomputes and returns results immediately.
- Tests distinguish successful zero rows from `$wpdb->last_error` failures.


FINDING G: LATER REBUILD-BATCH ENQUEUES ARE NOT VERIFIED

Area: Code & Functionality / Reliability
Impact: Medium
Status: Confirmed in source; proposed
Relevant code: includes/class-indexer.php, do_process_batch(),
               enqueue_first_batch(), and retry_rebuild_scheduling()

Version 1.9.1 correctly verifies that the first Action Scheduler enqueue
returns a nonzero action ID and falls back to a bounded WP-Cron retry. The two
places that enqueue a continuation after processing a batch still discard the
return value. If either enqueue fails, `wcs_is_indexing` remains true with no
job driving the rebuild.

The admin status endpoint can detect and resume this state, but only while an
administrator keeps the Turbo Search page open. There is no equivalent
automatic recovery for a continuation lost after the first batch, so a large
catalog rebuild can remain stalled indefinitely on an unattended site despite
the new first-batch protection.

Recommended solution:

- Route every continuation enqueue through one helper that verifies the
  returned action ID.
- On failure, schedule the same bounded WP-Cron retry used for the initial
  batch, carrying the current cursor and epoch rather than restarting at zero.
- Preserve the epoch guard so retries from superseded rebuilds exit harmlessly.

Tradeoffs and risks:

- Retry state becomes cursor-specific and needs cleanup after success or a new
  rebuild. Reusing the existing epoch-scoped retry pattern keeps it bounded.
- Do not mark indexing complete merely because scheduling failed; preserve the
  live table and surface the existing actionable error state after exhaustion.

Acceptance criteria:

- Every next-batch enqueue is checked for success.
- A failed continuation enqueue recovers without an administrator opening the
  settings page.
- Retry exhaustion preserves the live index and produces a clear admin error.


FINDING H: PUNCTUATED TITLES LOSE EXACT, PREFIX, AND PHRASE RANKING SIGNALS

Area: Search Algorithm & Relevance
Impact: Medium
Status: Confirmed by source comparison; proposed
Relevant code: includes/class-query-normalizer.php, normalize(),
               includes/class-indexer.php, title/title_padded fields,
               includes/class-search-handler.php, ranking expressions

Queries replace punctuation with spaces before tokenization, but indexed titles
and `title_padded` retain their original punctuation. Ranking then compares the
normalized query directly with the unnormalized title. A search such as
`t-shirt`, `men's jacket`, or a slash-separated model name can match through
FULLTEXT tokens, yet fail the exact-title, title-prefix, and whole-phrase boosts
because `t shirt` is not equal to or a literal phrase inside `T-Shirt`.

These are common product-name shapes. The product remains findable, but a title
that is effectively an exact shopper query can rank below less precise products
because the strongest deterministic signals disappear.

Recommended solution:

- Precompute a normalized title using the same punctuation splitting,
  whitespace collapse, and lowercase rules as Query_Normalizer::normalize(),
  plus a padded normalized-title representation for word/phrase boundaries.
- Apply exact-title, prefix, and phrase boosts to normalized fields. Keep the
  original title for display and FULLTEXT indexing unless benchmarks justify a
  wider schema change.
- Rebuild existing index rows through the normal schema-version migration.

Tradeoffs and risks:

- Adds one bounded text field and a rebuild on upgrade. Replacing the current
  `title_padded` field rather than adding a second padded field can control
  storage if live comparison proves semantic parity for unpunctuated titles.
- Normalization makes punctuation variants equivalent. That is desirable for
  search intent but should be covered for model names where punctuation may be
  meaningful.

Acceptance criteria:

- Punctuation-equivalent exact titles receive the same deterministic boost as
  unpunctuated exact titles.
- Existing ordering for ordinary unpunctuated titles does not regress.
- Tests cover apostrophes, hyphens, slashes, repeated whitespace, and model
  names containing punctuation.

2026-09-05 SECOND HIGH-IMPACT REVIEW: DISPOSITION AND IMPLEMENTATION
---------------------------------------------------------------------

Each of Findings D-H was independently verified against the actual 1.9.1
source (and, for E, against WooCommerce's own core hook dispatch on
thogotodeli.com's live installation) before touching anything — same
discipline as the prior review. All five held up as real, and all five were
implemented, though D and E were each scoped narrower than the reviewer's
literal recommendation for reasons explained below.

FINDING D — accepted, implemented with a narrower resolution than proposed.

Verified: do_process_batch()'s per-product fallback did increment
$batch_failures on a thrown exception, but $wpdb->replace() returning false
(the actual, common failure shape for a bad connection or a lock-wait
timeout) is not a Throwable — it was silently ignored in both the fallback
path and the live-table incremental-update path, exactly as reported.

Implemented: do_index_single_product()'s two replace() calls (the staging
parity write and the primary write) now check their return value, log the
product ID and $wpdb->last_error, and throw — which do_process_batch()'s
existing try/catch already turns into a counted batch failure, and which
surfaces a plain incremental update as a failed action in Action Scheduler's
own admin log instead of vanishing. A new wcs_rebuild_failed_count option
(reset per rebuild, incremented only for staging-table failures) is read
back at the final swap.

Not implemented as literally proposed: blocking the swap whenever any
unresolved failure occurred, or validating staging's row count against the
eligible-product count. The reviewer's own tradeoffs section already named
the failure mode of the stricter version: "one pathological product can
prevent a new index from shipping" — discarding an otherwise-complete
rebuild over a single bad row is worse for most stores than shipping it with
a named gap. Implemented instead: the swap still happens, but
wcs_last_rebuild_error is now set to a new 'partial_failure' code (distinct,
actionable admin message, logs carry the specific product IDs) instead of
silently reporting success. Separately, the pre-existing "every product in
the batch failed" halt path (batch_failures === processed_in_batch) — which
already preserved the old index correctly — previously cleared
wcs_is_indexing with no error at all; it now sets 'batch_write_failed' too,
closing a real but narrower silent-success gap in the code the reviewer was
pointing at.

Acceptance criteria met: a failed single-row REPLACE is now detected on both
paths; a rebuild where every attempted write failed never swaps; the admin
gets a specific, actionable error either way; tests cover a lone failure
inside an otherwise-successful rebuild (swap proceeds, 'partial_failure') and
a fully-failed batch (no swap, 'batch_write_failed').
Acceptance criterion NOT met by design: "one failed product cannot be
skipped while the rebuild reports success" — a partial failure is reported,
not silent, but the rebuild is not blocked by it. Revisit only if a future
report shows partial-failure rebuilds are common enough that surfacing
alone isn't sufficient — not before.

FINDING E — accepted, implemented in full, plus one adjacent gap closed.

Verified live against thogotodeli.com's own WooCommerce core
(class-wc-product-variation-data-store-cpt.php,
class-wc-product-data-store-cpt.php): a variation save fires
woocommerce_update_product_variation / woocommerce_new_product_variation
(never woocommerce_update_product or save_post_product — the post type is
product_variation, not product), and a variation stock change fires
woocommerce_variation_set_stock_status, never
woocommerce_product_set_stock_status — core gates the two on
is_type('variation') and fires exactly one. None of these three hooks were
registered anywhere in this plugin. Confirmed the reviewer's claim exactly.

Implemented: all three hooks now resolve the variation ID to its parent
(wp_get_post_parent_id() — a plain post lookup, not a full wc_get_product()
load, since this can fire once per edited row in the variations admin UI)
and queue the parent through the existing per-request-deduplicated
queue_product_update(). on_product_trash()/on_product_delete() (previously
hard-gated to post_type === 'product', silently doing nothing for a
variation) now queue the parent for a trashed/deleted variation instead of
doing nothing.

Adjacent gap closed opportunistically, not explicitly asked for: restoring
a product OR a variation from the Trash goes through wp_untrash_post(), a
raw core operation that never calls WC_Product::save() — so neither the
hooks above nor woocommerce_update_product ever fires for a restore, parent
or variation. A new untrashed_post handler covers both. This was a natural,
near-zero-cost extension of the exact hook wiring already being added for
variations, not a separate initiative.

Not implemented: a stronger "merge SKU-prefix hits as ranked candidates"
style enhancement was never proposed here — that remains Finding B's
deliberately deferred follow-up from the prior review, unrelated to this one.

Acceptance criteria met: changing, creating, deleting, trashing, or
restoring a variation refreshes its parent; multiple variation hooks firing
in one request still enqueue at most one parent update (existing
$queued_ids/as_has_scheduled_action guard, unchanged); tests cover all of
the above plus the untrash cases.

FINDING F — accepted, implemented in full.

Verified: $wpdb::get_results() returns an empty array both for a genuine
zero-row match and for a failed query() call — flush() resets last_result to
array() before query() ever reaches the row-population loop a failure would
skip, so the two cases are byte-for-byte identical from get_rows()'s return
value alone. $wpdb->last_error is the only side channel, and get_rows()
was suppressing it without ever reading it back.

Implemented: get_rows() now checks $wpdb->last_error after every query and
records it (a per-request static flag, mirroring the existing
$last_corrected_query pattern) plus a Logger::log() call at 'error' level.
handle_request() checks that flag once, after query_database() returns: if
results are empty AND a query in this request failed, the mutex is
released, nothing is written to either cache layer, and the response carries
an X-WCS-Query-Error header instead of being treated as a confident "no
results". A failure inside a tier whose results were later superseded by a
real match from a different tier is not flagged — only an empty final result
matters, matching the actual risk (caching a false negative), not every
transient blip.

Not implemented: rate-limiting the error log itself. A sustained outage
could produce one log line per search request for its duration; this
matches the existing, unthrottled logging convention everywhere else in this
codebase (Indexer::log() has no rate limiting either), and adding one would
be new infrastructure for a problem (log volume during a DB outage, which
already has bigger problems) nobody has reported.

Acceptance criteria met: a DB error is never written to APCu or the result
transient; the mutex is released on the failure path; a subsequent healthy
request recomputes normally (nothing was cached to prevent it); tests
distinguish a genuine zero-row response from a flagged query-error response.

FINDING G — accepted, implemented in full.

Verified directly in the 1.9.1 source: do_process_batch()'s two
continuation enqueues (mid-batch, when the time budget is hit; end-of-batch,
handing off to the next cursor) both called as_enqueue_async_action()
directly with the return value discarded — the exact same failure shape
1.9.1 had already fixed for the *first* batch only.

Implemented: enqueue_first_batch() was generalized into
enqueue_batch_with_retry( $last_id, $epoch ), used by schedule_full_rebuild()
for the first batch and by both continuation call sites in
do_process_batch(). retry_rebuild_scheduling() now takes the cursor as a

What was a real, fixable gap: a single retry (bulk write fails once, falls

2026-09-05 THIRD HIGH-IMPACT CODE AND SEARCH REVIEW (VERSION 1.10.0)
-------------------------------------------------------------------

Scope: a fresh source review after the 1.10.0 release, limited to failures
that can materially truncate, stale, expose, or misrepresent search results.
The previously documented candidate-window benchmark and Finding D's explicit
degraded-swap policy remain open and are not repeated as new findings here.

FINDING I: A FAILED PRODUCT-ID QUERY IS TREATED AS END OF CATALOG

Area: Code & Functionality / Rebuild integrity
Impact: High
Status: Confirmed by source inspection; proposed
Relevant code: includes/class-indexer.php, do_process_batch(), product-ID
               get_col() and empty($products) finalization branch

do_process_batch() reads the next page of eligible product IDs through
$wpdb->get_col(), but never checks $wpdb->last_error or the query return. An
SQL failure produces an empty value with the same shape as a genuine end of
catalog. If staging already contains any rows, execution enters finalization
and swaps that partial index into production.

This is more severe than an individual failed product write: one transient
failure while fetching a later batch can omit every product after the current
cursor while the rebuild reports completion.

Recommended solution:

- Check the batch-selection query for a database error before evaluating
  empty($products).
- Throw or enter the existing bounded batch retry path on failure; never run
  finalization from an indeterminate query result.
- Record a specific rebuild error after retry exhaustion and preserve the live
  table.

Tradeoffs and risks:

- A database outage delays completion, which is preferable to publishing an
  index whose catalog coverage is unknown.

Acceptance criteria:

- A simulated get_col() failure cannot execute RENAME TABLE.
- The same cursor is retried, and exhausted retries leave the live index and
  an actionable error state intact.


FINDING J: REBUILD SETUP AND ATOMIC SWAP SQL RESULTS ARE NOT VERIFIED

Area: Code & Functionality / Rebuild integrity
Impact: High
Status: Confirmed by source inspection; proposed
Relevant code: includes/class-indexer.php, schedule_full_rebuild() and
               do_process_batch() finalization

The CREATE-LIKE and TRUNCATE statements that prepare staging ignore their
return values. Finalization likewise ignores DROP/RENAME results and proceeds
to clear the indexing state, bust caches, and fire wcs_index_rebuild_complete
as though the swap succeeded.

A failed TRUNCATE can leave rows from an earlier abandoned rebuild in staging;
the next build uses REPLACE rather than recreating the complete table, so
products deleted since that abandoned run can be resurrected when staging is
swapped. A failed RENAME reports a false success and can leave schema migration
or configuration changes unapplied while downstream completion hooks run.

Recommended solution:

- Verify CREATE-LIKE and TRUNCATE before setting rebuild state or enqueueing
  the first batch.
- Verify the atomic RENAME result before dropping anything further or marking
  the rebuild complete.
- On failure, retain whichever table is currently live, set a distinct
  setup/swap error, and leave enough state for an administrator or bounded
  retry to recover safely.

Tradeoffs and risks:

- Recovery must account for the actual table names after DDL failure. Inspect
  table existence before retrying instead of assuming the rename occurred.

Acceptance criteria:

- Failed staging creation/truncation never starts a rebuild.
- Failed RENAME never clears the error, updates last-indexed time, busts the
  cache as a successful rebuild, or fires the completion hook.
- Tests cover stale rows remaining after a failed TRUNCATE.


FINDING K: THE FAILED-ACTION RETRY ENQUEUE CAN STILL DISAPPEAR SILENTLY

Area: Code & Functionality / Background-job reliability
Impact: High
Status: Confirmed by source inspection; proposed
Relevant code: includes/class-indexer.php, on_batch_action_failed()

Normal initial and continuation enqueues now verify Action Scheduler's return
value, but on_batch_action_failed() has a separate retry path that calls
as_enqueue_async_action() directly and discards the returned action ID. It
sets the per-cursor retry transient before attempting the enqueue. If Action
Scheduler returns zero, no retry job exists, the transient says the retry was
already consumed, and wcs_is_indexing remains true indefinitely.

Recommended solution:

- Route this retry through the same verified enqueue/WP-Cron recovery helper,
  or check its action ID and schedule the cursor/epoch WP-Cron retry on failure.
- Mark the retry transient only after a job has actually been accepted, or
  clear it when enqueueing fails.

Tradeoffs and risks:

- Ensure the Action Scheduler failure callback and WP-Cron retry budget share
  one bounded attempt policy so two recovery mechanisms cannot loop each other.

Acceptance criteria:

- Returning zero from the failed-action retry enqueue cannot leave indexing
  active without either a queued action or cron event.
- Tests cover this exact callback path, not only normal continuation enqueue.


FINDING L: INCREMENTAL UPDATES, DELETIONS, AND CACHE INVALIDATION CAN FAIL
SILENTLY

Area: Code & Functionality / Live-index freshness
Impact: High
Status: Confirmed by source inspection; proposed
Relevant code: includes/class-indexer.php, queue_product_update(),
               delete_single_product(), and trigger_cache_bust()

The incremental product-update enqueue discards Action Scheduler's returned
action ID. Both live and staging $wpdb->delete() calls discard database
failures. The debounced cache-bust schedule also discards its returned action
ID and sets the request-local `bust_queued` flag regardless of whether an
action exists.

These paths are the normal mechanism keeping search synchronized between full
rebuilds. A rejected update enqueue can leave a changed product stale
indefinitely. A failed deletion can keep a trashed, deleted, hidden, or newly
password-protected product searchable. A lost cache-bust action can continue
serving the pre-update result for the full 24-hour transient lifetime even if
the index write itself succeeded.

Recommended solution:

- Verify incremental update and cache-bust enqueue IDs and use a bounded
  fallback such as WP-Cron when Action Scheduler rejects them.
- Check both deletion results. Retry transient failures asynchronously and log
  a durable actionable error after exhaustion.
- Set in-request deduplication flags only after an existing or newly accepted
  action is confirmed.
- For security-sensitive removals, perform an immediate cache-version bump
  after a successful live delete rather than waiting five minutes.

Tradeoffs and risks:

- Reliable fallback scheduling adds small bookkeeping overhead to product-save
  hooks. The work itself remains asynchronous.
- Immediate invalidation on removal increases cache churn only for uncommon
  delete/hide events and prevents obsolete public results from lingering.

Acceptance criteria:

- A zero action ID cannot silently discard the only incremental update or
  cache invalidation.
- Failed live/staging deletes are detected and retried or surfaced.
- A successfully removed or hidden product cannot be returned from an old
  server cache for five minutes.


FINDING M: DATABASE-ERROR RESULTS ARE STILL CACHED IN THE BROWSER

Area: Code & Functionality / User experience
Impact: Medium
Status: Confirmed by source inspection; proposed
Relevant code: includes/class-search-handler.php, X-WCS-Query-Error response;
               assets/js/search.js, doSearch() and performSearch()

The server now correctly avoids transient and APCu writes whenever a search
query encounters a database error. The JavaScript client does not read
X-WCS-Query-Error, however. It caches every successful JSON response unless it
has the separate X-WCS-Indexing marker. A degraded partial or empty response is
therefore retained in the page's in-memory cache and reused for the same query
until reload, even after the database has recovered.

Recommended solution:

- Read X-WCS-Query-Error in doSearch() and attach a non-enumerated response
  marker using the same pattern as __indexing, or return structured metadata.
- Do not insert marked responses into the browser cache. Render recovered rows
  if present; render the existing temporary-error state for an empty degraded
  response.

Tradeoffs and risks:

- Array-attached metadata is convenient but fragile across serialization. A
  small structured response envelope is clearer long term, though it requires
  coordinated server, MU-plugin, and frontend changes.

Acceptance criteria:

- A response carrying X-WCS-Query-Error is never stored in the page cache.
- Repeating the query after database recovery performs another request.
- Partial recovered rows remain usable without being presented or retained as
  a fully reliable result set.

1. Product-update WP-Cron scheduling can still fail silently (High).

queue_product_update() checks the Action Scheduler action ID, but its fallback
wp_schedule_single_event() result is discarded. retry_product_enqueue() also
discards the result when scheduling its next attempt. If WP-Cron refuses either
event, no update action or retry event remains and the product can stay stale
indefinitely. This is the same second-layer scheduling failure already handled
by schedule_retry_or_fail() for rebuild batches.

Recommended resolution: add a verified product-retry scheduling helper, check
both WP-Cron calls, and record a durable, admin-visible incremental-sync error
when no retry event can be created.

2. A permanently failed deletion leaves restricted products searchable
(High).

delete_with_retry() makes three immediate attempts, but after the final failure
it only writes a WooCommerce log and returns. The calling path then continues
normally. A trashed, deleted, hidden, or newly password-protected product can
therefore remain in the public search index indefinitely if no later event
successfully removes it.

Recommended resolution: enqueue a delayed, bounded deletion retry after the
immediate attempts fail, persist enough context to retry both live and staging
when applicable, and expose an unresolved-removal error to administrators after
exhaustion. Do not treat logging alone as completion for a public-visibility
removal.

3. Successful security-sensitive removals still use delayed cache invalidation
(High).

delete_single_product() calls the ordinary debounced trigger_cache_bust() after
deletion. Existing transient results may therefore continue returning a
deleted, hidden, or password-protected product until the five-minute debounce
action executes. This does not meet Finding L's acceptance criterion that a
successfully removed or hidden product cannot be returned from an old server
cache for five minutes.

Recommended resolution: immediately call execute_cache_bust() after a
successful live-table removal. These events are uncommon compared with normal
product writes, so the correctness benefit outweighs the additional cache
turnover.

4. Cache invalidation can still be lost until cache expiry (Medium).

trigger_cache_bust() now leaves its request-local flag false after a rejected
Action Scheduler call, allowing another write in the same request to retry.
That does not guarantee another write will occur. If this was the request's
last or only index update, and no later product change happens, existing search
results remain stale for the full 24-hour transient lifetime.

Recommended resolution: give cache invalidation a checked WP-Cron fallback or
perform an immediate cache-version bump when scheduling fails. The latter is
simple, bounded, and guarantees correctness without another background chain.

5. Product retry counters can leak into later independent failures (Medium).

retry_product_enqueue() returns when as_has_scheduled_action() finds an existing
update action but does not delete wcs_product_retry_{product_id}. A later update
failure for the same product within the transient lifetime can inherit the old
attempt count and exhaust its retry budget early. The initial successful path
in queue_product_update() likewise does not clear a stale counter.

Recommended resolution: delete the per-product retry transient whenever an
existing action is confirmed or a new action is successfully accepted. Tests
should cover a failed enqueue followed by an independently queued action and a
later new failure for the same product.
