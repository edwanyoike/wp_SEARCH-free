1. EXECUTIVE SUMMARY
======================================================================

Submission verdict: NOT READY FOR WORDPRESS.ORG SUBMISSION

Version 1.6.0 resolves all three blockers from the 1.5.1 review:

- The prohibited/high-risk 100-product indexing quota was removed.
- PHPCS now passes cleanly.
- readme.txt was reduced below 10 KB by moving older history to changelog.txt.

The Pro upsell presentation was also substantially improved. Disabled fake
controls were removed and the main Settings screen now contains one compact
Pro card after the functional Free settings.

However, this deeper review found three new release blockers:

1. The 1.6.0 ZIP includes the obsolete internal 1.5.1 review report, which
   states that the plugin is not ready and describes already-fixed problems.
2. Cached searches served by the MU cache-bypass plugin ignore the new
   administrator-configured rate limit and always use 60 requests/minute.
3. The MU cache-bypass plugin prefers an installed Pro directory even when Pro
   is inactive, which can execute inactive Pro code and diverge from the active
   Free plugin's behavior.

Additional medium-severity findings:

- The translation POT file is stale and incomplete.
- The manual data-reset action flushes the entire WordPress object cache.
- Network activation/deactivation/uninstall only processes 1,000 sites.
- WooCommerce compatibility metadata is substantially behind the currently
  published WooCommerce release and needs a tested update.

BLOCKER 2 — MU FAST PATH IGNORES CONFIGURED RATE LIMITS
Severity: HIGH / RELEASE BLOCKER

Normal REST behavior:

includes/class-search-handler.php:69-70 reads:

- wcs_rate_limit_requests
- wcs_rate_limit_window

The Settings UI allows administrators to configure these values.

MU fast-path behavior:

mu-plugin/wcs-cache-bypass.php calls Rate_Limiter::allow() with hardcoded
values:

- maximum requests: 60
- window: MINUTE_IN_SECONDS

Impact:

- If an administrator configures 10 requests/minute, uncached requests are
  limited at 10 but cached requests continue until 60.
- If an administrator configures 200 requests/minute, cached requests are
  rejected after 60 while uncached requests remain allowed.
- The effective limit changes depending on cache state.
- The documented setting does not control all search traffic.
- A bot can favor warmed queries to bypass a stricter merchant-configured
  limit.

Existing test gap:

CacheKeyParityTest verifies that the MU path uses the same counter key and that
calls increment it. It tests only the old/default 60-per-minute behavior and
does not assert parity with non-default administrator settings.

Required remediation:

- Read wcs_rate_limit_requests and wcs_rate_limit_window in the MU path.
- Apply the same lower bounds used in Search_Handler::check_permissions().
- Ideally centralize option resolution in code shared by both paths so they
  cannot drift again.
- Preserve the identical wcs_rl_<md5(ip)> counter key.

Required tests:

- A configured maximum of 1 or 5 rejects the next cached request at the same
  point as the normal REST route.
- A configured maximum above 60 does not reject the 61st cached request.
- A non-default window reaches Rate_Limiter::allow() unchanged.
- Default behavior remains 60 requests per 60 seconds.


BLOCKER 3 — MU PATH CAN EXECUTE AN INACTIVE PRO EDITION
Severity: HIGH / RELEASE BLOCKER

Location:

mu-plugin/wcs-cache-bypass.php:53 onward

Current behavior:

The MU plugin searches these directories in this order:

1. turbo-search-for-woocommerce-pro
2. turbo-search-for-woocommerce

It selects the first directory whose class-query-normalizer.php file exists.
It then determines Pro status by checking whether class-license.php exists.

It does not check whether the selected edition is active.

Failure scenario:

1. A site has both Free and Pro directories installed.
2. Pro is deactivated, while Free is active.
3. The Pro directory remains on disk, which is normal WordPress behavior.
4. The MU intercept selects Pro because Pro is checked first.
5. It loads Pro's Query_Normalizer and Rate_Limiter from an inactive plugin.
6. It marks the request as Pro and enables Pro currency cache-key behavior.
7. The active Free REST handler still uses Free behavior and the default
   currency cache key.

Potential consequences:

- Cache-key mismatch and systematic cache misses.
- Execution of code belonging to an inactive plugin.
- Version-skew failures if inactive Pro is older or newer than active Free.
- Class-definition conflicts later in the request.
- Pro-only currency behavior leaking into the Free fast path.
- Fatal errors if the inactive edition's expected companion files or APIs are
  incompatible.

Why existing checks do not cover this:

- Free/Pro mutual exclusion only prevents both editions being active.
- It does not remove the inactive edition's directory.
- Current CacheKeyParityTest executes the Free repository's MU source in an
  isolated test setup and does not model two installed directories with only
  Free active.

Required remediation:

- Select the edition from WordPress's active plugin state, including network
  activation on multisite.
- Never infer activation from directory/file existence.
- Load code only from the active edition.
- If active-edition state cannot be resolved safely, skip the MU fast path and
  allow WordPress to dispatch the normal REST route.
- Retain a safe fallback for custom folder names without scanning and
  preferring inactive known folders.

Required tests:

- Free active, Pro installed but inactive: Free normalizer selected.
- Pro active, Free installed but inactive: Pro normalizer selected.
- Both directories present, neither active: fast path skipped.
- Network-active edition on multisite: correct edition selected.
- Selected edition missing required file: fast path skipped without fatal.
- Different Free/Pro versions installed: inactive edition is never loaded.

FINDING 5 — MANUAL DATA RESET FLUSHES THE ENTIRE OBJECT CACHE
Severity: MEDIUM

Location:
includes/class-admin-settings.php:482

Current behavior:

ajax_delete_all_data() calls wp_cache_flush(). This clears the complete shared
WordPress object cache, not only Turbo Search entries.

Impact:

- WooCommerce and unrelated plugins lose their cached objects.
- A large production store may experience a cache stampede and database load
  spike immediately after the operation.
- The action exceeds the scope suggested by "Delete All Plugin Data."

Positive controls:

- The operation requires a valid nonce.
- The operation requires manage_options.
- It is explicitly initiated by an administrator.

Recommended remediation:

- Delete/invalidate only known Turbo Search option and transient cache keys.
- Increment the plugin cache version to invalidate search-result keys.
- Avoid a global cache flush.
- Add a test asserting ajax_delete_all_data() does not invoke
  wp_cache_flush().


FINDING 6 — MULTISITE LIFECYCLE STOPS AFTER 1,000 SITES
Severity: MEDIUM

Locations:

- includes/class-activator.php:95
- includes/class-activator.php:140
- uninstall.php:78

Current behavior:

Network activation, deactivation, and uninstall select at most 1,000 blog IDs.

Impact on networks above 1,000 sites:

- Later sites may not receive tables/options during network activation.
- Later sites may retain scheduled events during network deactivation.
- Later sites may retain plugin tables and options after opted-in uninstall.

Documentation mismatch:

readme.txt answers Multisite support with an unqualified "Yes." The code only
fully manages networks up to 1,000 existing sites, although newly created sites
are handled separately.

Recommended remediation:

- Iterate sites in bounded pages using get_sites() fields => ids.
- Restore blog context after every iteration, including failure paths.
- Add tests around pagination or document the 1,000-site operational limit.

FINDING 9 — REMOTE PROMO REMAINS A HUMAN-REVIEW RISK
Severity: LOW / POLICY RISK

Positive controls now present:

- Only shown on the plugin's own settings screen.
- Dismissible per administrator.
- Message sanitized through wp_kses_post().
- Link escaped.
- HTTPS required.
- Link host restricted to ozulabs.com or ozupay.com.
- Common tracking/referral parameters rejected.
- External request disclosed in readme.txt.
- Static edition identifier is the only explicit query payload.

Residual concern:

The promotional message and destination change remotely without a plugin
release. A WordPress.org reviewer cannot fully assess future content from the
submitted code. The HTTP request also exposes ordinary connection metadata to
the service host.

Safest option:

- Remove remote promotions from the WordPress.org edition.

Acceptable risk-controlled option:

- Keep the first-party allowlist and tracking rejection.
- Never serve third-party advertisements.
- Never add site/user/product/search data to the request.
- Keep every notice dismissible and plugin-screen-only.
- Keep the readme disclosure synchronized with behavior.

8. SECURITY REVIEW RESULTS
======================================================================

AJAX handlers
-------------

Administrative handlers reviewed:

- wcs_dismiss_notice
- wcs_rebuild_index
- wcs_get_index_status
- wcs_delete_all_data

Each uses a specific nonce and requires manage_options before performing its
operation. No authorization bypass was found.

The public wcs_refresh_nonce handler intentionally has no incoming nonce or
capability requirement because it only creates a public guest REST nonce. It
is rate-limited per IP. This is not an authorization boundary; the REST search
serves public catalog data.


REST endpoint
-------------

- Namespace/route: wcs/v1/search
- Method: GET
- Query is sanitized with sanitize_text_field().
- The wp_rest nonce is verified.
- The normal route uses a per-IP rate limiter.
- Product results are public catalog data.

No direct state-changing public REST operation exists.


Input handling
--------------

Reviewed uses of GET, POST, SERVER, and COOKIE data. Inputs are unslashed and
sanitized before use. The read-only settings-tab query parameter is sanitized
and safelisted. No unsafe file-upload or deserialization path exists.


Output escaping
---------------

Reviewed PHP-rendered output in all view templates and admin notices. Dynamic
text, attributes, URLs, and remote promo content use the appropriate escaping
or allowed-HTML functions. No confirmed XSS finding was identified.


SQL
---

Direct queries generally use $wpdb->prepare(), including %i identifier
placeholders for table names. Dynamic search SQL is prepared by its callers
before reaching the small get_rows() execution helper. No confirmed SQL
injection finding was identified.


Filesystem
----------

MU-plugin installation/removal uses the WordPress filesystem API with the
direct method only, avoiding credential prompts and raw copy/unlink calls.
No user-controlled filesystem path was found.


External requests
-----------------

One outbound application request exists: the disclosed first-party promo
fetch. It uses wp_remote_get(), a five-second timeout, response/error checks,
sanitization, and transient caching.
